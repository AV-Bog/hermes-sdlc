# Архитектурные решения

Последняя правка - 10 ноября 2026.

Ссылки вида `файл.py:123` - строки в исходниках Hermes v0.21.4; они лежат в
`~/.hermes/hermes-agent`. Номера строк относятся именно к этой версии: после обновления Hermes
они сдвинутся, тогда искать по имени хука, а не по номеру. Номер раздела в скобках, например
[§4](#права-по-этапам), ведёт к этому разделу этого документа.

## 1. Форма поставки

Python-плагин в `HERMES_HOME/plugins/hermes-sdlc/`: работает внутри процесса Hermes,
регистрирует хуки и свои инструменты, подтверждений от человека не требует. Манифест требует
только `name` - `hermes_cli/plugins_manifest.py:322`.

## 2. Хуки

| Хук | Роль | Где в коде |
|---|---|---|
| `pre_tool_call` | гейт: возвращает `{"action": "block"}`; при таймауте закрывает действие | `hermes_cli/plugins.py:1801-1845`, `plugins_dispatch.py:48, 205-212` |
| `pre_llm_call` | строка «этап, что запрещено, чего ждём», попадает в ход через `{"context": "..."}` | `agent/turn_context.py:730-783` |
| `pre_verify` | подталкивание «не заканчивай», лимит 3 из ядра; получает `changed_paths`, `attempt`, `coding` | `hermes_cli/plugins.py:1915-1940` |
| `post_tool_call` | счётчики вызовов, блокировок, нарушений | - |
| `on_session_start` | инициализация прогона; в payload `session_id`, `model`, `platform` | `agent/conversation_loop.py:770-777` |

Хуки стоят на всех трёх путях вызова инструментов (`model_tools.py:773`,
`agent/tool_executor.py:653`, `agent/agent_runtime_helpers.py:2349`). Исключение внутри колбэка
действие разрешает и пишет одну строку в лог (`plugins_dispatch.py:213-217`), поэтому свои
исключения плагин ловит сам и отвечает `block`.

Токены плагин не считает: `hermes -z --usage-file` пишет их сам. Поле `usage` есть и в
`post_api_request` (`agent/turn_response_intake.py:58-100`), но это дублирование.

Своя конфигурация: `ctx.get_config("key")` (`hermes_cli/plugins.py:257`).

## 3. Этапы

Три этапа: `design → code → verify`.

`design` включает опрос человека (функциональность, цели, ограничения, масштаб), проектирование
архитектуры и выяснение того, что уже есть: в проекте, в документации, в установленных
инструментах. Читать можно, запускать нельзя - любой запуск это исполнение кода ([§4](#права-по-этапам)). Результат
этапа - `design.md` с функциональностью, требованиями, архитектурой и списком файлов.

`code` - реализация объявленной архитектуры. Тесты, пришедшие в проект, не правятся.

`verify` - вход по объявленному: все файлы из списка в `design.md` есть на диске. Правки
существующих файлов на этом этапе разрешены (иначе найденное не исправить), запрещены новые
файлы, правки тестов и переписывание архитектуры.

Первоначально вход в `verify` был «в проекте появился код»: первый же написанный файл закрывал
этап, и работа вставала после первой строки. Условие по объявленным файлам требует сверки
объявленного с файлами - пока её нет в коде, плагин считает два этапа (`design → code`), а шаг
проверки держится текстом напоминания и хуком `pre_verify`.

Тесты отдельным этапом не идут. Режим с тестами и режим без тестов - настройка, а не этап; в
режиме с тестами тесты приходят в проект из требований и на этапе кода не правятся. Критика
архитектуры, потолки длины и вопросы с ценой - позже.

## 4. Права по этапам

Права выдаются не «что запрещено», а «что разрешено»: на каждом этапе плагин держит закрытый
список инструментов, а всё, чего в списке нет, блокируется. Причина - спайк M0: чёрный список
по именам инструментов обходится, субагент обошёл три запрета записью через `browser_exec`
([§15](#спайк-m0-результаты-первого-прогона)). Белый список закрывает и `browser_exec`, и `computer_use`, и
любой инструмент, который появится в Hermes позже.

| Этап | Можно | Нельзя |
|---|---|---|
| `design` | запись `design.md`, чтение и поиск | код, тесты, запуск кода, всё остальное |
| `code` | код, чтение, `terminal`, `execute_code`, правки `design.md` | правки тестов, которые уже лежат в проекте |
| `verify` | правки существующих файлов, запуск проверок | новые файлы, правки тестов, изменения архитектуры |

Проверить допущение запуском на этапе плана нельзя: любой запуск - это исполнение кода, то есть
та же лазейка, что найдена спайком. Допущения, которые не проверяются чтением, идут в раздел
«Вопросы и допущения» и остаются вопросом к человеку, а не поводом запустить питон.

Белый список решает, **какими инструментами** можно работать; **какие файлы** ими можно менять -
решают правила путей ([§8](#защита-от-обхода), появляются в M2). В M1 есть только список инструментов, поэтому этап
`code` разрешает запись вообще, а защищённые файлы держатся текстом напоминания.

Список разрешённых инструментов на этапе - не догма, а поле конфига: у пользователя бывают свои
инструменты (MCP, плагины), и запрещать их молча нельзя. По умолчанию он собран из ядра Hermes;
всё, что не перечислено, блокируется с сообщением «разрешено только …» - так агент понимает,
что это запрет этапа, а не поломка.

Правки `design.md` на этапе кода разрешены: это мелкая работа, которую агент делает сам по
ходу. Каждая правка пишется в журнал, в отчёте - строка «перепроектирований: N».

Тесты на этапе кода править нельзя: иначе проверка подгоняется под код.

## 5. Один файл `design.md`

Разделы: «Функциональность», «Требования», «Архитектура», «Вопросы и допущения». В
«Архитектуре» - интерфейсы и **список файлов**: каждый путь отдельной строкой от корня проекта
(`src/parser.py`). По этому списку считается вход в `verify` ([§7](#переходы)); свободным текстом его не
проверить, поэтому формат путей обязателен, а не украшение.

Других файлов в целевом проекте до этапа кода не создаётся.

## 6. Состояние

Этап - функция от содержимого проекта, пересчитывается на каждом `pre_tool_call`.

`state.json` хранит режим (`off` / `advisory` / `enforce`), счётчики, ответы человека, историю
нарушений. Файлы: `.sdlc/state.json`, `.sdlc/log.md`, `.sdlc/reports/`.

Подписи нет: этап определяется артефактом, подделывать нечего.

## 7. Переходы

`design → code` - в `design.md` есть функциональность, требования, архитектура с интерфейсами и
список файлов. `code → verify` - все объявленные файлы существуют на диске. `verify` - конец
прогона.

Вход в `verify` сейчас проверяет сам агент по тексту напоминания: автоматической сверки
объявленного с файлами ещё нет ([§11](#отложено)).

Этап идёт только вперёд, назад - командой человека.

## 8. Защита от обхода

Снимок хешей защищённых путей, сверка после каждого вызова, откат, счётчик нарушений. Проверка
через `lstat`: подмена файла симлинком не считается тем же файлом.

Тесты запускает агент в проекте. Целостность файлов тестов держится на сверке хешей и откате.

Запрет на запись держится на именах инструментов, и это дырявое место, проверенное спайком
([§15](#спайк-m0-результаты-первого-прогона)): субагент, получив блокировки `write_file`, `terminal` и
`execute_code`, записал файл через `browser_exec` - это локальный Python со стандартной
библиотекой. Поэтому права выдаются белым списком на этап ([§4](#права-по-этапам)): всё, что не перечислено как
разрешённое, блокируется, включая `browser_exec`, `computer_use` и инструменты, которых в
Hermes ещё нет. Перечень «пишущих» инструментов остаётся только в режиме `advisory` - там он
нужен для счётчика «агент пытался писать на этапе плана», а не для защиты.

## 9. Сбои

| Сбой | Поведение |
|---|---|
| корень проекта не найден | не блокировать, запись в лог |
| исключение в своём коде | плагин ловит сам и отвечает `block` |
| таймаут хука | закрыто блокирует ядро |
| подмена защищённого файла | откат и нарушение |
| `mode: off` | хуки не регистрируются |
| плагин не загрузился | прогон помечается невалидным (см. `bench/README.md`) |

## 10. Корень проекта

`ctx.get_config("root")` → `HERMES_SDLC_ROOT` → корень git → текущий каталог. Корень нужен
только чтобы найти `design.md` и `.sdlc/`. Работает плагин или нет - решает человек конфигом:
включён - контролирует, выключен - нет. Сам себя не выключает.

## 11. Отложено

Тесты (режим, запуск), критика архитектуры во второй сессии, потолки длины `design.md`, вопросы
человеку с вариантами и ценой, `sdlc_check_dependency`, сверка объявленных интерфейсов с
файлами.

## 12. Отвергнуто

| Что | Почему |
|---|---|
| `sdlc_ask_user` | вопрос и так возможен, нужна блокировка до ответа |
| белый список команд терминала | произвольную shell-команду заранее не разобрать |
| `post_api_request` для токенов | дублирует `--usage-file` |
| подпись `state.json` | этап выводится из артефакта, подделывать нечего |

## 13. Что не решено

- Гейт проверяет наличие раздела, а не работу: три строки в `design.md` открывают код.
  Лечится только внешней оценкой, а не плагином.
- Как считать «соблюдён ли порядок этапов» - метода нет.
- Автоматическая сверка объявленных файлов с диском: вход в `verify` пока держится текстом
  напоминания ([§3](#этапы), [§7](#переходы)).
- Сверка объявленного с сделанным: как считать, не решено.
- Цена принуждения может оказаться выше выгоды на простых задачах - это и есть вопрос замера.
- Две сессии в одном проекте одновременно: `state.json` под файловой блокировкой, иначе гонка.
- Плагин не включён ни у кого по умолчанию: `plugins.enabled` требует ручной записи.
- Обход закрыт белым списком ([§4](#права-по-этапам)), но появился обратный риск: устаревший список блокирует
  легитимную работу - новый безопасный инструмент или MCP-сервер пользователя. Список придётся
  вести руками, и в `advisory` перечень пишущих инструментов остаётся чёрным: он нужен только
  для счётчика «агент пытался писать на плане», а не для защиты.

## 15. Спайк M0: результаты первого прогона

Одноразовый плагин-пробник (`bench/spike/`) и семь сценариев: `block-all`, `terminal`,
`subagent`, `yolo`, `verify`, `nudge`, `allowlist`. Цель - проверить механизм хуков до начала
разработки плагина. Прогоны 9 ноября 2026, Hermes v0.21.4, `deepseek-flash`:
7 прогонов, 144 с, 41 вызов модели, 96 513 токенов, $0.0195.

| Что проверялось | Результат |
|---|---|
| блокировка из `pre_tool_call` в `-z` | работает: вызов не выполняется, текст блокировки приходит агенту как ошибка инструмента |
| `write_file`, `patch`, `terminal`, `execute_code` | блокируются одинаково |
| вызовы из субагента | хуки срабатывают, `task_id` свой; **но блок обходится инструментом вне списка** |
| `pre_llm_call` | текст доходит до модели в 41 запросе из 41; приклеивается к пользовательскому сообщению, системный промпт не меняется |
| `--yolo` | хуки не снимает |
| `pre_verify` | вызывается при попытке закончить после правок; ответ `continue` продлевает работу, предел - `agent.max_verify_nudges` (3) |
| `--usage-file` | 21 поле; субагентов считает только деньгами |

**Субагент и `browser_exec`.** В сценарии с запретом `write_file`, `patch`, `terminal`,
`execute_code` субагент получил три блокировки подряд и создал файл через `browser_exec` -
это локальный Python со стандартной библиотекой, а не только браузер. После перехода на белый
список (тот же сценарий, разрешены только `read_file`, `search_files`, `delegate_task`) файлов
в проекте ноль, а `browser_exec`, `computer_use` и инструменты вне списка блокируются - правило
записано в [§4](#права-по-этапам) и [§8](#защита-от-обхода).

**Права.** Разрешается перечисленное, всё остальное блокируется: список запретов стареет вместе
с Hermes, и новый инструмент с исполнением кода становится дырой молча. Обратная цена -
устаревший белый список блокирует легитимную работу ([§13](#что-не-решено)).

**Реализация.** Состояние ведётся по `task_id`, потому что субагент - отдельная
задача в той же сессии. Гейт проверки реализуем через `pre_verify` с бюджетом продолжений.
Счётчик нарушений держится на `post_tool_call`: он вызывается и после заблокированного вызова,
а в результате лежит текст блокировки. Номер вызова в журнале спайка не писался, поэтому
плагин запоминает, что заблокировал, до `post` и сверяет свой список, а не текст ошибки.
Цена прогона берётся из `session_model_usage`, а не из `usage.json`: файл включает субагентов
в деньги, но не в вызовы и токены (4 против 12 вызовов, 11 483 против 22 360 токенов).

**Не проверено:** поведение хуков в интерактивном TUI и в шлюзе (проверен только `-z`),
`pre_verify` внутри субагента, инструменты с побочными эффектами помимо перечисленных.
Дом без `model.default` в `config.yaml` даёт `HTTP 400` с пустым именем модели - поэтому дом
прогона собирается только из шаблона.
