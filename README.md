# hermes-sdlc

Плагин для Hermes Agent, который принуждает агента проходить этапы разработки.

Агент не переходит к следующему этапу, пока не создан артефакт предыдущего нужного
вида. Завершённость этапа определяется проверкой артефакта.

## Зачем

LLM-агенты пишут код по одному запросу и объявляют результат готовым, не
проверяя его. Пользователь обнаруживает дефекты сам — то есть делает ту
работу, ради которой он к агенту и обратился.

Существующие решения закрывают задачу частично:

| Решение | Чего не хватает |
|---|---|
| Хосты агентов (Hermes, Claude Code, Codex) | нет понятия «этап разработки» |
| Workflow-движки (Temporal, XState, BPMN) | не контролируют агента: он может соврать о результате |
| Мультиагентные системы (ChatDev, MetaGPT) | нет внешней проверки: конец фазы объявляет сам агент |
| Spec-driven (Spec Kit, Kiro, BMAD) | соблюдение порядка ничем не проверяется |

Ни одно не совмещает состояние процесса с возможностью принудительно
заблокировать действие агента. В этом и состоит задача проекта.

## Как это работает

1. **Этапы.** Интервью, архитектура, тесты, код, сверка. Этап тестов
   пропускается, если тесты не нужны. Все артефакты живут в одном файле
   `design.md` в корне целевого проекта.
2. **Состояние процесса.** Три файла в `.sdlc/`: машинный `state.json` с текущим
   этапом и критериями, читаемый журнал `log.md` и папка `reports/` с разборами.
   Писать в них может только плагин.
3. **Переход по артефакту.** Этап меняется, когда появился артефакт нужного вида.
   Отдельной функции перехода нет, поэтому её нельзя не вызвать.
4. **Блокировка.** Хук `pre_tool_call` возвращает `{"action": "block"}` и не даёт
   выполнить действие, запрещённое текущим этапом: на этапе архитектуры это код,
   на этапе кода - тесты.

## Статус

Стадия исследования. Проведён анализ предметной области, сформулирована
постановка задачи, проверена техническая выполнимость. Реализация не начата))))

## Планируемая проверка

Сравнение трёх режимов на наборе задач:

- **A** — одиночный промпт;
- **B** — мягкий режим: этапы описаны скилом, принуждения нет;
- **C** — жёсткий режим: этапы закреплены хуком, переход по гейту.

Задачи берутся из двух источников: своя песочница и готовые сборники задач.

Метрики: доля задач, прошедших внешние тесты; число ложных «готово» (агент
объявил завершение без выполнения критериев); цена в токенах и итерациях.

Цена замеряется, чтобы ответить на вопрос стоит ли принуждение своих денег. 
Оно добавляет итераций, повторов и объяснений,
но экономит переделки, и без цифры выбор между мягким и жёстким режимом остаётся
вопросом вкуса. Токены берутся из поля `usage`, которое приходит на каждый запрос
к модели, итерации считаются по числу вызовов инструментов.

Замер не является целью продукта. Он входит в первую версию и убирается из
итоговой.
